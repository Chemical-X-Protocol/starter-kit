### Worktree index seed: a fresh worktree's first q starts from the main checkout's rows (epic #6745, K8b #6769)

Measured by K8 (#6753): a fresh git worktree's first `chemx q` parsed every file, 4.8 s idle and 7.0 s under load for 1,406 files, because `.chemx/index.db` is per checkout and the main checkout's cannot be copied (it also holds the board, and it is stamped for its root). Reference: [agent-workspace.md](agent-workspace.md), timings in [index-freshness.md](index-freshness.md).

- `chemx worktree add` now seeds the new worktree's index from the main checkout's (#6769): the main db is attached read-only and the index rows (files, symbols, props, hooks, imports, embeddings, full-text) of every file whose bytes hash to the content the parent indexed are copied in one transaction, with the worktree file's own mtime and size; the first q then parses only the files that differ. One output line: `index: seeded N of M files from <main> (Tms)`. `--no-seed-index` skips it and creates no `.chemx`.
- A worktree made by plain `git worktree add` gets the same seed on its first index-backed command (`q`, `read`, `audit`, the MCP tools); that answer's index line ends with `; seeded N of M files from <main>` (JSON: `index.freshness.seed`).
- Never copied: `project_stamp` (the worktree's own is written at open), `violations` and `audit_snapshots` (audit output; the worktree's audit rebuilds them), the forge `pattern_*` tables, and every team, lock, lease, feed, agent, session and usage row. A parent index built by another extractor version, one without content hashes, a busy parent db or an unreadable one is `seed from parent skipped: <reason>` and the first q indexes from disk; a main checkout without an index says nothing. Two first syncs racing on one new worktree seed it once (the emptiness is re-checked inside the write transaction).
- The seed never waits on the parent: `withoutBusyRetry(db, fn)` in `cli/team/coordination-busy.js` turns the 30 s busy retry off for one call, so a held parent db fails after a 500 ms `busy_timeout` and the sync carries on from disk.
- Measured (index-freshness.md, 2026-10-25, three interleaved rounds, medians, other agents running): kit, 1,553 files, main checkout index current: first q 5.9 s before, 1.0 s with the seed in the sync (plain `git worktree add`), 0.7 s after `chemx worktree add` (seed 140-190 ms inside the add), 0 files re-indexed; with a main checkout index a few hours behind (1,390 files lent of 1,553): 5.8 s to 2.5-2.7 s, 313 files parsed. do-it-for-the-xp, 1,644 files: 11.3 s to 2.0 s, 1 file re-indexed, where a warm q is 1.8 s on that machine.
- Not changed: the index freshness guarantee (seeded rows are hash-checked once on the first sync, like any row synced within 2 s of its file, then trusted by mtime and size); `worktree remove`; the board's refusal to open a copied db. Not covered: a parent index that is stale against the parent's own disk only lends the files it has (the kit's working copy lent 1,240 of 1,553 files in one run because its index was a few hours behind); the rest are parsed.
